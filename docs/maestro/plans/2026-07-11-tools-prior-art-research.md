# Prior-Art Research: Tool Loops, Reasoning Replay, Loop Memory

**Status:** complete (2026-07-11). Feeds the design map's open item #3 and sanity-checks settled items #2/#4. Sources at bottom.

## 1. Reasoning/thinking-block replay during tool use (gated decision — now resolved)

**Anthropic (native thinking):** thinking blocks **must** be passed back unchanged in the last assistant message during tool use. Modifying, stripping, or rearranging them → HTTP 400 (`thinking blocks … cannot be modified`). Blocks carry a cryptographic `signature` field that must round-trip intact. The documented most-common bug is *exactly* the naive implementation: code that filters content blocks by type or rebuilds assistant messages instead of echoing them. Interleaved thinking (thinking between tool calls) follows the same preservation rules. Thinking cannot be toggled mid-turn.

**OpenRouter normalization:** reasoning is configured via a unified `reasoning` parameter (effort levels for OpenAI/Grok, token budgets for Anthropic/Gemini). For multi-turn tool use, reasoning must be echoed back via `message.reasoning` (plaintext) and/or `message.reasoning_details` (structured array — required for encrypted/summarized reasoning types). Their docs state the sequence of reasoning blocks "must match the outputs generated by the model during the original request; you cannot rearrange or modify."

**Implication for Maestro — one sentence:** wire-truth must be **object-level, not string-level**. The runner's message list stores each assistant turn as the complete message object (content, `tool_calls`, `reasoning`, `reasoning_details`) and echoes it verbatim; never rebuild from parsed text. Consequences:
- Our `<thought>` tag parsing becomes one of two *presentation* sources: use `reasoning`/`reasoning_details` when the model emits native reasoning, else parse tags. The wire copy is untouched either way.
- No persistence problem: the message list is per-node and ephemeral; frozen replay reuses *tool results*, never assistant messages, so encrypted reasoning_details never need to live in logs. Logs keep the human-readable reasoning text.
- This confirms the wire-truth invariant settled in #3 and shows the naive alternative isn't just worse — on Anthropic models it's a hard API error.

## 2. Cross-round loop memory (gated decision — now resolved)

**Reflexion (the paper, NeurIPS 2023):** stores *distilled natural-language reflections* ("lessons") in an episodic memory buffer across trials and conditions the next attempt on them — not full trajectories. Reported gains: +11 pts coding, +20% reasoning. This is the strongest prior-art validation of the `rounds` digest carrying `## Changes`-style deltas rather than full outputs.

**LangGraph reflection agents (blog + examples):** the naive pattern — state is a message list, every generator/reflector call appends, full history carries forward. Works at short horizons; it is exactly the quadratic-cost/stale-anchoring pattern at longer ones, and LangGraph's own default `recursion_limit` of 25 plus their documented "the agent is stuck, not the task too complex" guidance shows where it goes.

**Implication for Maestro:** the customizable digest spans both prior-art styles — `digest: { section: Changes }` (default) is Reflexion-style distilled memory; `digest: { section: output }` reproduces LangGraph-style full-output carryover for archetypes that want it (e.g. debate). The mechanism as designed needs no change; **finalize it.**

## 3. Termination & error handling (sanity-check of settled #2 — confirmed)

- **Caps are universal:** LangGraph `recursion_limit` (default 25), OpenAI Agents SDK `max_turns` (`MaxTurnsExceeded`), Dify agent node max iterations (default 5), Flowise `MAX_LOOP_COUNT`.
- **The forced final turn is validated by others' pain:** the Agents SDK's plain `MaxTurnsExceeded` termination has a known failure mode — users can't retrieve the last output or tool result when the cap hits, and the SDK added `error_handlers["max_turns"]` to return "a controlled final output instead of ending the run with the error." Maestro's cap-hit → one `tool_choice: "none"` call is that fix designed-in.
- **Error-as-tool-result is the standard:** LangGraph `ToolNode`'s `handle_tool_errors` catches tool exceptions and returns them as a `ToolMessage` so the model can self-correct. Matches Maestro's errors-local decision exactly. Their guidance worth stealing: *invest in good tool error messages* — that's what lets the model reason its way out instead of looping.

## 4. Streaming vocabulary (sanity-check of settled #4 — confirmed, one noted divergence)

Vercel AI SDK v5's SSE part types map ~1:1 onto Maestro's vocabulary:

| Vercel AI SDK | Maestro |
|---|---|
| `tool-input-start` | `tool_pending` |
| `tool-input-delta` | *(deliberately omitted in v1)* |
| `tool-input-available` | `tool_call` |
| `tool-output-available` | `tool_result` |

The divergence: AI SDK v5 streams partial tool-call args by default (live-typing the args in the UI). Maestro v1 skips this (partial JSON adds client complexity for marginal UX); the `tool_pending` → `tool_call` pair leaves room to add an args-delta event later without reshaping anything.

## 5. Misc observations

- Dify's agent node (default 5 iterations, users filing issues to raise it) suggests defaults matter: Maestro's `maxToolTurns` default should be generous enough not to strangle real research loops (~8–10) while still bounded.
- LangGraph's recursion-limit issue threads repeatedly show agents looping on *repeated identical tool calls*; a cheap mitigation to consider at implementation time: detect identical (tool, args) repeats within a node and inject a nudge into the tool result ("you already made this exact call; the result has not changed").
